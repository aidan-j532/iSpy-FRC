# Configuration Reference

The runtime loads `Config/config.json` relative to its current working directory. In a repository checkout, run iSpy from the repository root and edit `<repo>/Config/config.json`. The provisioned service's working directory is `/opt/iSpy`, so the current runtime reads `/opt/iSpy/Config/config.json`.

The provision script also writes `/etc/iSpy/config.json` and sets an `iSpy_CONFIG` environment variable, but the current boot/runtime code does not read that variable. For the version in this repository, edit the file under `/opt/iSpy/Config/` used by the service, not the unused copy under `/etc/iSpy/`.

The config is not one giant single structure with random values. It is a nested dictionary with a few major blocks:

- top-level runtime settings
- `camera_configs`
- `plugins`
- `rollback`
- `model_profiles`

## Default config structure

A minimal generated config looks roughly like this:

```json
{
  "device": 0,
  "unit": "frc",
  "debug_mode": true,
  "app_mode": true,
  "health_stale_threshold": 1.0,
  "camera_configs": {
    "default_cam": {
      "name": "default_cam",
      "camera_type": "opencv",
      "source": 0,
      "subsystem": "field",
      "calibration": {
        "distance": 0.0,
        "game_piece_size": 0.0,
        "size": 0,
        "fov": 0
      },
      "pipeline": {
        "name": "object_detection",
        "settings": {
          "vision_model": {
            "file_path": "YoloModels/pytorch/_default_v26_detect_for_fuel.pt",
            "source_pt": "YoloModels/pytorch/_default_v26_detect_for_fuel.pt",
            "min_conf": 0.5,
            "optimize": "off",
            "quantize": false
          }
        }
      }
    }
  },
  "plugins": {
    "trackers": {},
    "utilities": {},
    "frame_processors": {}
  },
  "rollback": {
    "enabled": true,
    "data_dir": "VideoRecordings",
    "fps": 30.0,
    "max_queue": 60,
    "downsample": 1,
    "segment_minutes": 5,
    "max_total_mb": 2048
  }
}
```

This is the config that the project creates on first boot. It is intentionally not empty. It contains the sane defaults that most installs can work from once a camera and model are filled in.

The example is deliberately shortened to the parts most people need to recognize. Boot may add camera IDs and model metadata, and the web UI can save more pipeline-specific settings. Use the running UI or the generated config as the source of truth for a particular install; do not replace the whole file with a small example just to change one value.

## Important top-level settings

These are the values most likely to affect a normal setup:

### `unit`

Controls the output unit used for geometry and detection coordinates.

Supported values include:

- `frc` - common FRC/WPILib convention; outputs in meters while calibration inputs remain in inches
- `meter`
- `inch`
- `foot`
- `centimeter`

This is important because robot code usually expects field-relative coordinates in meters, while calibration values are often entered in inches.

### `debug_mode`

Turns on extra visualization overlays in the UI and in the stream. This is primarily useful during setup and calibration.

### `app_mode`

Controls whether the full web dashboard is active. It can be toggled in a normal session and also used in a game mode flow that temporarily disables the web UI for a run.

### `health_stale_threshold`

Number of seconds before the health module reports a degraded state when a frame has not arrived in time.

### `max_fps`

Optional hard cap on pipeline FPS. A value of `0` leaves the cap disabled; set a positive value when the machine is overloaded or a camera is producing more frames than the robot needs.

### Logging and pipeline choices

- `log_level` controls the minimum severity written to the log. The default is `INFO`.
- `log_file` is the runtime log path; by default it is `Outputs/log.txt`, relative to the current working directory.
- `admin` exposes experimental pipeline choices such as QR code and optical flow in the pipeline selector. Leave it off unless you need those options.
- `model_profiles` stores reusable model-backed pipeline settings saved by the web UI. It is managed automatically and usually does not need hand editing.

Here is the short version of the root-level settings that affect day-to-day use:

| Setting | Default | Practical meaning |
| --- | --- | --- |
| `unit` | `frc` | Camera geometry and calibration inputs use inches; position outputs use meters. |
| `debug_mode` | `true` | Enables additional visual debugging information. |
| `app_mode` | `true` | Starts the local dashboard with the vision runtime. |
| `health_stale_threshold` | `1.0` | Seconds without fresh loop/frame activity before health is marked degraded. |
| `max_fps` | `0` | No global loop cap when `0`; a positive value caps the runtime loop. |
| `metrics` | `true` | Enables runtime metrics collection. |
| `admin` | `false` | Shows the experimental QR-code and optical-flow choices in the pipeline selector. |
| `log_level` | `INFO` | Minimum severity for the runtime log. |
| `log_file` | `Outputs/log.txt` | Log path, resolved from the working directory. |

The default values can move as the project changes. The generated file and web editor are authoritative for the version you have installed.

## Camera config entries

Each camera lives under `camera_configs` and has its own settings.

Example:

```json
"camera_configs": {
  "front_cam": {
    "name": "front_cam",
    "source": "/dev/video0",
    "camera_type": "opencv",
    "subsystem": "field",
    "fps_cap": 30,
    "yaw": 0,
    "pitch": 0,
    "height": 1.0,
    "x": 0,
    "y": 0,
    "calibration": {
      "distance": 24,
      "game_piece_size": 3.5,
      "size": 120,
      "fov": 70
    },
    "pipeline": {
      "name": "object_detection",
      "settings": {
        "vision_model": {
          "file_path": "YoloModels/pytorch/my_model.pt",
          "source_pt": "YoloModels/pytorch/my_model.pt",
          "min_conf": 0.5,
          "optimize": "auto"
        }
      }
    }
  }
}
```

Important camera fields:

- `source` - camera path, device index, video file, or URL
- `camera_type` - camera backend type, often `opencv`
- `subsystem` - usually `field` for robot field-relative vision
- `yaw`, `pitch`, `height`, `x`, `y` - camera mount angles and offsets. Angles are in degrees; distances use the top-level `unit` setting.
- `fps_cap` - optional per-camera frame-rate cap
- `grayscale` - whether the camera frames are converted to grayscale
- `calibration.distance` - distance used during calibration
- `calibration.game_piece_size` - target real-world size in inches
- `calibration.size` - pixel size at that reference distance
- `calibration.fov` - camera FOV in degrees

Keep the camera's identity/source fields on the camera entry and pipeline options under `pipeline.settings`. This makes it possible to switch pipelines without carrying unrelated settings from the old one. The web editor handles that separation and removes settings that do not belong to the selected pipeline.

For example, a second camera is another entry with its own `source`, `pipeline`, and mount. It does not need its own global `unit` or `plugins` block:

```json
"camera_configs": {
  "front_cam": {
    "name": "front_cam",
    "source": 0,
    "camera_type": "opencv",
    "pipeline": {
      "name": "object_detection",
      "settings": {
        "vision_model": {
          "file_path": "YoloModels/pytorch/fuel.pt",
          "source_pt": "YoloModels/pytorch/fuel.pt",
          "min_conf": 0.5
        }
      }
    }
  },
  "rear_cam": {
    "name": "rear_cam",
    "source": 1,
    "camera_type": "opencv",
    "pipeline": {
      "name": "april_tag",
      "settings": {}
    }
  }
}
```

This is just the `camera_configs` value, not a complete config file. Use camera sources that exist on the actual machine; index `1` is only an example and is not guaranteed to be the rear camera.

With the default `unit: "frc"`, mount distances are entered in inches and detections are output in meters. The known-object calibration wizard also asks for object size and distance in inches. Keep these units consistent when editing the JSON by hand.

## `pipeline` and `vision_model`

The pipeline block is important. For object detection, you will usually see:

```json
"pipeline": {
  "name": "object_detection",
  "settings": {
    "vision_model": {
      "file_path": "YoloModels/pytorch/model.pt",
      "source_pt": "YoloModels/pytorch/model.pt",
      "min_conf": 0.5,
      "optimize": "auto",
      "quantize": false
    }
  }
}
```

The `vision_model` block is where the actual model is selected and tuned. The project expects a real model path and generated metadata sidecars next to the model when possible.

The common `vision_model` values are:

| Value | Meaning |
| --- | --- |
| `file_path` | The model artifact the pipeline should load. Initially this is usually the `.pt` source model; after optimization it may point to the selected artifact. |
| `source_pt` | The original PyTorch model used as the source for optimization and model selection. |
| `min_conf` | Detection confidence threshold; increase it to reject more weak detections, or lower it if valid targets are being missed. |
| `optimize` | `off`, `auto`, or a conversion path such as `onnx`. The result depends on pipeline support and installed runtime packages. |
| `target_format` | Requested output when optimization is enabled; `auto` lets iSpy choose from the options available on that system. |
| `quantize` | Requests quantization for conversion paths that support it. Check the output against the original model. |
| `quantization_dataset` | Optional image folder used by backends that need calibration samples. |

Do not assume that editing `file_path` to an accelerator extension installs or enables that accelerator. The file, model metadata, runtime package, and target device all need to agree. Start with the `.pt` model and a known input before testing an optimized copy.

## Add-ons and plugin entries

Add-ons are enabled by their presence in the config. There is no separate `enabled` flag in the config. If the entry exists, it is enabled.

Example:

```json
"plugins": {
  "trackers": {
    "FRC/object_tracker": {
      "distance_threshold": 0.5,
      "stale_threshold": 1.0
    }
  },
  "utilities": {
    "FRC/network_table_handler": {
      "network_tables_ip": "10.0.0.2"
    }
  },
  "frame_processors": {}
}
```

This style is a little different from older configs, but it is the pattern the project uses now. Remove a plugin entry to disable it.

## Rollback and recording

Rollback is a core feature and is not an optional plugin. It is configured in the top-level `rollback` block.

```json
"rollback": {
  "enabled": true,
  "data_dir": "VideoRecordings",
  "fps": 30.0,
  "max_queue": 60,
  "downsample": 1,
  "segment_minutes": 5,
  "max_total_mb": 2048
}
```

This does a few things:

- records a session for each run
- writes `.avi` files per camera
- stores JSON sidecar data with frame-level detections and robot pose
- rotates sessions and keeps disk usage bounded
- allows replay of old sessions

## When to edit the config directly

The web UI is the safer choice for routine camera and model changes because it validates fields and saves the right nested structure. Direct JSON editing is useful when:

- you are editing a machine in a clean environment
- you want to move a config between systems
- you are debugging a malformed camera entry
- you are creating a saved config for a new robot setup

If you edit the file by hand, keep a backup and preserve valid JSON syntax. Stop and restart the runtime so it reloads the values. The web app may save changes immediately, but camera pipeline/model settings can still require a vision restart to take effect.

Make a copy before a bigger edit:

```bash
cp Config/config.json Config/config.json.bak
```

On PowerShell:

```powershell
Copy-Item .\Config\config.json .\Config\config.json.bak
```

When troubleshooting a config edit, reduce the change to one setting and restart. If the process is already running, it may still be using the config it loaded at startup.

## Important gotcha

The repo is opinionated about where model and config files live. The default model layouts and metadata files are expected to be in the `YoloModels/` tree. If you move or rename things without updating the config, the pipeline will not be able to find the model correctly.

That is one of the most common setup issues. The config path and the model path must match on disk.
