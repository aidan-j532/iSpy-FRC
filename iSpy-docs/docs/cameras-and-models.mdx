# Cameras and Models

The project is only as good as the camera setup and the model it is using. A lot of the real work is done in the web UI, but it still helps to understand what is going on under the hood.

## Camera sources

A camera in the project is usually defined by a `source` value and a `camera_type`.

Typical examples:

```json
"source": 0
```

for a built-in webcam, or:

```json
"source": "/dev/video0"
```

for a USB camera on Linux. Some setups also use file paths or network streams.

The config supports multiple camera types, but the common case is `opencv`, which is the default that ships with the project.

The source is interpreted by the selected camera backend. A number such as `0` is a local camera index; `/dev/video0` is a Linux device path; a URL or image/video path is not a local USB camera and should not be diagnosed by looking only for `/dev/video*`. Device numbering can change when USB cameras are unplugged or moved to another port, so check the source list on the machine you will actually deploy.

An FRC setup often has a USB camera on a coprocessor and a separate driver-station camera. The latter is not automatically a vision source: add only the camera that this iSpy process is meant to read. If adding a second camera, test it by itself first, then check both feeds and the combined loop rate.

The set of accepted `source` values depends on the backend:

| `camera_type` | Source forms |
| --- | --- |
| `opencv` | Integer index (`0`, `1`), `/dev/videoN`, a network URL (`rtsp://`, `http://`, `udp://`), or a path to an image or video file. |
| `tello` | A `udp://` URL. If you leave `source` as an index or anything that is not a `udp://` URL, the backend fills in `udp://0.0.0.0:11111` for you. |
| `replay` | A recorded session, used internally by the rollback player. You do not add this one by hand. |

The Tello backend talks to the drone over UDP before OpenCV sees any video, so it also reads three companion keys: `tello_ip` (default `192.168.10.1`), `tello_command_port` (default `8889`), and `tello_video_port` (default `11111`). Those defaults match a stock Tello in its own access-point mode.

An image file source is treated as a still frame that the camera hands back on every read, which is the point of it: you can point a pipeline at a fixed picture and check the model without a physical camera. Video files and network streams go through OpenCV like a device and run at whatever rate the source produces. A still image is the only source that is defined to never change.

## Camera setup workflow

For a first camera, use this order:

1. Open **Cameras** in the web UI and add or select the camera.
2. Choose a source that exists on this machine, then confirm that the live frame appears.
3. Choose the pipeline. For a detector, start with `object_detection`.
4. Select a model and confirm that detections appear before changing thresholds.
5. Set the camera's physical mounting values and calibrate the lens or known-object scale if the pipeline needs it.
6. Restart vision after changes that the UI says need a restart, then verify the result in the live view.

A common mistake is to set up a camera path in theory but forget that the system needs a real video device behind it. If the camera source is not correct, the pipeline will never produce useful frames.

Before tuning a model, check the image itself. The lens should be focused, exposure should not wash out the target, and the camera should be mounted firmly. A detector cannot recover detail that the camera never captured. Change brightness/exposure with care as well: an image that looks nicer on a stationary workbench may blur when the robot is moving.

## Pipeline choice

The project supports several pipeline names, but the common default is `object_detection`.

That is the path most teams will use when they want bounding boxes and field-relative positions from a model. The code is structured around having `pipeline.name` plus a `pipeline.settings` block for pipeline-specific data.

When a camera uses a model-backed pipeline, the `vision_model` block must be present and should point to a real model file. If it is missing, the project will warn or fail during setup.

The runtime also uses model metadata, usually stored in a sidecar next to the original model. It describes things such as task, labels, and input dimensions. Keep the sidecar with the model when copying files between machines. A model file that exists but has the wrong task or missing labels can be just as confusing as a missing file.

## Model storage

Models are stored under a `YoloModels` tree. The default layout looks roughly like this:

```text
YoloModels/
  pytorch/
  onnx/
  tflite/
  rknn/
  openvino/
  coreml/
  engine/
```

The project also writes metadata sidecars next to a model when it can. Those sidecars help the runtime know things like:

- model task
- class names
- input size
- output format
- expected metadata for conversion

This matters because the code is not just guessing based on file extension; it reads metadata where possible.

## Device identity

A camera entry can carry a `device_id`, a stable string that discovery assigns from the hardware itself rather than from its position in the list. On Windows it is derived from the USB `VID`/`PID` and interface path. On Linux it is built from the sysfs node behind `/dev/videoN`.

The reason it exists is that indices move. Plug a second camera in and `0` and `1` can swap; unplug one and the surviving camera's index can shift. The index is a convenience for a fixed rig, and `device_id` is what survives changes.

Two features key off it:

- Boot cleanup. When iSpy starts and a configured camera's device is not detected, the entry is removed and its settings are written to `Save/camera_profiles.json` under its `device_id`. Re-adding the same hardware can refill those settings. The cleanup never removes the last camera, because the runtime needs at least one to boot.
- Camera profiles. The Lightbox profile button stores and restores a camera's tuning and calibration under its `device_id`.

Exporting a config through the Settings page strips `device_id` from every camera, since it is machine specific. Re-importing on another machine leaves the entries without IDs until you pick devices again, so cleanup and profiles will not match until then.

Discovery also filters out things that look like video nodes but are not cameras. On Linux it reads the V4L2 capabilities and drops memory-to-memory codec nodes such as `bcm2835-codec-decode`, which claim capture capability without being a camera. On Windows it ignores the generic names the OS hands out when it has nothing better. If a camera you know exists does not appear in the discovery list, that filter is the usual reason.

## Default model behavior

On first boot, `ispy-boot -f` creates the model folders and downloads the default models. That is why a fresh install often needs internet at least once.

The exact default model used is project-specific and can change over time, but the key point is that a default path is created for you so the first camera setup has something to work with.

The Models page is mainly for managing PyTorch `.pt` source models. Uploading/selecting a source model is separate from converting it: iSpy may generate an optimized artifact later, and the camera can continue using the source while that work happens. Do not delete a model that is marked active, and do not copy an optimized file into the `pytorch` folder just because its filename looks similar.

### What the sidecar actually holds

The metadata sidecar is written next to a model when the runtime can inspect it, and the boot sequence makes sure every `.pt` in `YoloModels/pytorch` has one. It records the model task, the class names and count, the input size, and the output layout. Those values are what the pipeline uses to decide how to interpret raw model output, which is why the task being right matters more than the file existing.

Two failure modes are worth separating:

- A missing sidecar. Boot tries to generate one by inspecting the model. If that fails, the camera starts but the pipeline reports that it cannot run, because it has no architecture to work from. The camera stays in the config; it just produces nothing until the model is fixed.
- A wrong sidecar. This is worse. A sidecar that describes a different task or a different class list loads without complaint and produces confidently wrong output. If a model was renamed, re-exported, or swapped on disk, regenerate its sidecar rather than reusing the old one.

### Profiles saved from the editor

The editor remembers validated model settings as a profile. When you save a camera that uses a model-backed pipeline, the runtime runs the pipeline's own profile check on the settings. If they pass, a snapshot is stored under `model_profiles.<pipeline>.<name>` and offered on the Load Profile tab of any camera using that pipeline. Because the check gates it, a profile never contains settings that cannot run; a broken configuration is simply not saved as a profile.

The snapshot is deep-copied, so editing the original camera afterward does not change the stored profile. Loading a profile copies its settings onto the camera you are editing. These profiles are a convenience for reusing a good setup across cameras, not a source of truth; the camera's own settings win for that camera.

Camera profiles are separate and keyed differently. A camera profile stores a camera's tuning and calibration under its `device_id` in `Save/camera_profiles.json`, which is also where boot cleanup parks the settings of a camera that was unplugged. Model profiles are keyed by pipeline and name.

## Model optimization and backend selection

The model settings have two related fields. `optimize` controls whether conversion runs (`off`, `auto`, or `onnx`); `target_format` chooses the format to build when conversion is enabled (`auto` lets iSpy choose from the formats supported by that pipeline and machine). The runtime can fall back to the original model or a CPU-capable path if an accelerator is unavailable, but it may run more slowly.

For example, a Rockchip board may use RKNN, an NVIDIA system may use TensorRT if its runtime is installed, and a machine without a supported accelerator can use ONNX on the CPU. See [Vision Pipelines and Backends](./vision-pipelines) for the supported targets and what each pipeline needs.

## Quantization

The config also supports `quantize`, which requests an INT8 artifact for formats that support it. Quantization can reduce model size or inference time, but it can also reduce detection accuracy. If you provide a `quantization_dataset`, use images representative of the camera, lighting, and targets where the robot will run; compare the optimized result against the original before deployment.

For a fair comparison, keep the camera, input size, and threshold fixed and use the same set of images. First check whether the same objects are found; then look at latency. If the result changes, tune or reject the converted artifact rather than assuming the speed gain is worth it. See [Datasets and Session Recordings](./datasets-and-recordings) for the dashboard's image collection and the separate session recorder.

## Choosing a good confidence threshold

The `min_conf` value is one of the most important settings in the model configuration.

A typical value is around `0.5`, but the correct value depends on:

- the camera quality
- the lighting of the field
- model quality
- whether there are visually noisy background objects

If you see too many false positives, raise the threshold. If the model misses too much, lower it. Most teams tune this during live testing.

## Calibration and size values

There are two different kinds of values here. The camera's mounting fields (`height`, `x`, `y`, `yaw`, and `pitch`) describe where the camera sits on the robot. The `calibration` object stores image measurements such as known-object size and distance, field of view, or ChArUco intrinsics. They are not interchangeable: a correct lens calibration cannot compensate for an incorrect camera mount offset.

Open **Calibrate** on a camera card for the ChArUco Intrinsics, Focal / FOV, or Pose Keypoints wizard sections supported by that pipeline and model. The wizard's **Reset calibration** action clears saved calibration values for that camera. See [Camera Calibration](./calibration) for board setup, measurements, and how to validate the result.

## The simplest working setup

For a first camera, aim for:

- a single real USB webcam or board camera
- a simple object-detection model
- a `min_conf` value around `0.4` to `0.7`
- known camera height and mounting pose
- at least one calibration point

This gives you a solid base before trying more advanced pipelines or special detectors.

## When a result does not look right

Use this order rather than changing several settings together:

1. Open the live feed and confirm focus, exposure, and source.
2. Make sure the intended pipeline and model are assigned to this camera.
3. Check the detected class and confidence before changing `min_conf`.
4. Check mount offsets and calibration only after the image-space detection makes sense.
5. If the model is optimized, compare with its `.pt` source on the same frame.

The [Configuration Reference](./configuration) shows where camera and model values live. If camera changes are saved but not visible in the running feed, restart iSpy; the current runtime does not rebuild an already-running pipeline in place.
