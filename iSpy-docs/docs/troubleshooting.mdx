# Troubleshooting and Operations

Start with the first error in the runtime log, then check the matching camera, model, or network setting below. The last message is not always the cause; earlier startup errors often explain why a later step failed.

It helps to split a vision problem into four questions: can iSpy start, can the camera deliver a frame, does the pipeline produce the right result, and can the robot read that result? Start at the first failing step. Forcing a fresh install before you know where it fails can erase the evidence and your config.

## Where to look first

Check these places first:

- `Outputs/log.txt`
- `journalctl -u iSpy -f` on a systemd deployment
- the local web UI health page
- the camera configuration page
- the model configuration page

For a terminal run, read `Outputs/log.txt` in the directory where you started iSpy. For a systemd service, start with `sudo journalctl -u iSpy -f`; the service may have a different working directory from your interactive shell.

## The most common issues

### 1. No cameras detected

This usually means one of these is true:

- the USB camera is not plugged in
- the camera path is wrong
- the wrong camera index is selected
- the system does not have permission to access the device

The boot process removes configured local devices that it cannot find. Check that the camera is plugged in before booting, then use **Cameras** in the web UI to confirm the selected source. On Linux, a USB camera commonly appears as `/dev/video0`; on Windows, try the available camera index from the source picker. Network streams and video files use their own paths and do not need a local camera device.

### 2. Wrong model path

This is one of the most common errors. If the config points to a model that does not exist, the project will eventually fail during model validation or pipeline construction.

Check that:

- the file exists on disk
- the path matches the config exactly
- the metadata sidecar exists if the model expects one
- the model is in the right `YoloModels/<format>/` folder

### 3. Slow or degraded health

A degraded health state usually means the system is not receiving fresh frames on time. This can happen when:

- the camera source is hung
- the model is too slow for the hardware
- the machine is overloaded
- the FPS cap is set too high for the system

Open the health page and compare the reported frame age and FPS with the runtime log. Lower `max_fps` or use a smaller model if the machine cannot keep up. The stale-frame threshold only changes when health becomes degraded; it does not make the camera or model faster.

### 4. First boot fails due to missing dependencies

First boot downloads the default models and may install backend-specific packages. Check the terminal output and `Outputs/log.txt` for the first error. Confirm that the machine has internet access, enough free disk space, and a backend supported by its operating system and hardware. The pipeline may still run on a CPU backend if an optional accelerator cannot be installed.

### 5. The dashboard opens, but the camera image is stale or missing

The web app can start before a camera is ready, so an open dashboard is not proof that frames are arriving. Check the camera card's status and the `/api/health` response, then confirm the source exists on the machine. For a local camera, unplug/replug it, check OS permissions, and try the camera's current device path or index. For a URL or file source, confirm that exact source can be opened by the selected camera type.

On a board, also check that another process is not holding the camera device. If you changed the source or camera type, restart iSpy so the runtime reconstructs the pipeline.

### 6. The image is good, but the detector misses targets or sees the wrong thing

Confirm that the right model is selected and that its metadata matches the model. Check the class name and confidence on a clear, still target. Lowering `min_conf` can reveal weak detections, but it also admits more false positives; raising it can hide valid targets. Fix focus, exposure, resolution, or model selection before trying to compensate with a very low threshold.

If you are using a converted model, compare it with the original `.pt` file using the same image. That tells you whether the problem is model quality or the optimized backend. The [model guide](./cameras-and-models) covers that comparison.

### 7. Boxes look right, but the position is wrong

Check the geometry separately from the detection:

1. Confirm `unit` and the units expected by robot code. In `frc` mode, camera/calibration distances are entered in inches and position outputs are meters.
2. Re-measure the camera's `height`, `x`, and `y` from the same robot reference point your team uses.
3. Check `yaw` and `pitch` signs; a reversed mount angle can look like a calibration failure.
4. Confirm that lens intrinsics or known-object FOV were calibrated at the current resolution and focus.
5. Compare a target at more than one known distance and position.

Do not change the camera's physical offsets to hide a bad detection or a wrong unit. The [calibration guide](./calibration) distinguishes camera mount values from image calibration.

### 8. NetworkTables is disconnected or the robot sees nothing

Check the built-in utility status and the first NetworkTables warning in `Outputs/log.txt`. Confirm that `network_tables_ip` is the roboRIO/server address and that the vision computer is on the robot network. Then check that the robot code uses the `VisionData` table, the same topic names, and the right value type. The default `vision_data` is a JSON string; a struct-array reader needs the `struct[]` publish type.

If the dashboard can connect but the roboRIO cannot, the issue is probably in the client/server address or network path, not the camera feed. See [Web UI and Networking](./web-ui-and-networking).

### 9. The optimized model does not load or is not faster

Confirm that the base `.pt` model works first. Then check the model status and logs for the selected format, installed runtime, and device. An accelerator file is not portable between all boards, and a conversion that succeeds on a desktop does not guarantee that the target board can load it. Compare timing under the same input size and frame conditions; conversion can be a regression as well as an improvement.

## Resetting the system

Do not use `ispy-boot -f` as a general repair or restart command. It deletes `Config/`, `YoloModels/`, `Outputs/`, and the active dataset directory, including files you may have added there. First save a copy of `Config/config.json`, then fix the specific error shown in the log and restart with `ispy-run` (or restart the systemd service).

Use `ispy-boot -f` only when you deliberately want to discard and recreate that generated state. Back up any custom models, datasets, configuration, and logs first. If the package code needs updating but the generated state should stay, update/reinstall the Python package in its environment without deleting those directories.

## Restarting the service

On a deployed Linux board, use `sudo` with the service commands:

```bash
sudo systemctl restart iSpy
sudo systemctl status iSpy
sudo journalctl -u iSpy -f
```

The service is the normal way to keep the pipeline running on startup. If the project is not being run as a service, `ispy-run` is the relevant command.

## Rollback and replay troubleshooting

The project records sessions under `VideoRecordings`. If you are debugging a model or camera issue, replaying an old session is often useful.

The code expects sessions to be replayed in a controlled way because replay does not publish live data to the robot. It is mainly a debugging and validation tool.

If a replay behaves differently than the original capture, it usually means:

- the model changed
- the config changed
- the camera setup changed
- the pipeline parameters changed since the original run

The recorded video is taken from raw camera frames, while the JSON sidecar stores the runtime detections and pose. Replaying it is useful for comparing what the camera saw with what the pipeline reported; it does not restart the old runtime configuration or publish detections to the robot.

## Useful log commands

For a provisioned Linux board:

```bash
sudo journalctl -u iSpy -f
tail -f /opt/iSpy/Outputs/log.txt
```

For a local PowerShell run, use:

```powershell
Get-Content .\Outputs\log.txt -Tail 100 -Wait
```

Press `Ctrl+C` to stop following either log.

## When asking for help

If the problem persists, include the first relevant error from `Outputs/log.txt`, the selected pipeline and model format, and the camera source when asking for help. Remove team numbers, IP addresses, or other private network details before sharing logs publicly.
