# CLI and Commands

Run iSpy commands from the project directory that contains `Config/`. The runtime uses the current working directory to find its config, generated models, recordings, and logs. On a provisioned board, that directory is normally `/opt/iSpy`.

If a command says there is no config even though you can see one in another folder, first check `pwd` (or `Get-Location` in PowerShell). iSpy does not automatically use the directory containing the installed Python package as the project data directory.

## Main commands

| Command | What it does |
| --- | --- |
| `ispy-boot` | Checks the existing setup, creates missing folders, prepares default models and validates the system. It does not start the live vision loop. |
| `ispy-run` | Loads `Config/config.json` from the current directory and starts the camera pipelines and web UI. |
| `ispy` | Provides `setup` and `start` subcommands. Both run the boot flow and then start the live vision loop. |
| `ispy-bench` | Benchmarks model/backend performance on the current machine. |
| `ispy-stats` | Compares model outputs and reports detection/performance statistics. |

The Python package installs these entry points; their definitions are in `pyproject.toml`.

## First setup

On a new checkout, initialize the generated files and default models once:

```bash
ispy-boot -f
```

Then start the live system:

```bash
ispy-run
```

`ispy-boot -f` (also written `ispy-boot --fresh`) is destructive. It deletes the current project's `Config/`, `YoloModels/`, `Outputs/`, and active dataset directory before recreating the defaults. That includes your edited configuration, downloaded or uploaded models, logs, and dataset files in those folders. Back them up before using this option; do not use it as a normal restart or troubleshooting step.

For an existing setup, use `ispy-run` to start vision. Running `ispy-boot` without `-f` prepares and validates the existing setup, but exits without starting the camera loop.

## `ispy-boot` options

```text
ispy-boot [-f] [-s] [-w]
```

- `-f`, `--fresh`: delete generated state and create a new default setup. Destructive; see the warning above.
- `-s`, `--service`: install and start the background service. This is intended for supported Linux service setups.
- `-w`, `--wait`: wait for configured camera pipelines to become ready before boot completes. This can take a while if a camera or model is unavailable.

`ispy-boot --help` prints the options available in the installed version.

`--wait` can be useful in a service or scripted startup when you want boot to report readiness before continuing. It can also make startup wait a long time while a model is downloading or a pipeline cannot become ready. For interactive troubleshooting, leave it off at first so you can inspect the live status and log.

`-s`, `--service` runs the service installer for the current platform. Treat this as a deployment action, not part of every development start; service installation may require elevated privileges and is intended for supported Linux setups.

## `ispy` subcommands

```bash
ispy setup
ispy start
```

`ispy setup` runs a fresh boot and then starts the vision loop. Because fresh boot removes generated state, only use it when you intend to rebuild the setup and have backed up anything you need. `ispy start` runs the normal boot checks against the existing config and then starts vision. Both accept the boot options `-s` and `-w`.

For clearer separation, the lower-level commands are often easier to use: run `ispy-boot -f` once on a new install, then use `ispy-run` for normal operation.

## Service commands on Linux

If you installed iSpy as a systemd service, manage it with:

```bash
sudo systemctl status iSpy
sudo systemctl restart iSpy
sudo systemctl stop iSpy
sudo journalctl -u iSpy -f
```

The provisioned image uses `/opt/iSpy` as its working directory, so the runtime reads `/opt/iSpy/Config/config.json`. The provision script also writes `/etc/iSpy/config.json`, but the current runtime does not load that copy. Check the service log with `journalctl` when it does not start; a service does not write output to the terminal where you ran another command.

Use `status` before restarting a service that appears offline. A repeated restart will not fix a missing camera, invalid config, or broken model path; the journal usually gives a more useful first error. The watchdog can restart the runtime after a failure, so check the timestamps and repeated startup lines when reading logs.

## Stop and restart

For a foreground run, press `Ctrl+C` in the terminal that is running `ispy-run`. The runtime handles shutdown and stops its cameras and recording worker. For a system service, use `systemctl stop` or `systemctl restart` instead of trying to kill an arbitrary Python process.

Avoid starting two copies of iSpy against the same camera and config. The second process may fail to open the device, compete for resources, or make it unclear which process owns the dashboard port.

## Benchmarking and model comparison

Run both tools from the project directory so their default config, images, and model paths resolve correctly.

### `ispy-bench`

This benchmarks inference backends using a `.pt` model. Defaults are five seconds per run and the backend iSpy recommends for the current machine.

| Option | Meaning |
| --- | --- |
| `--duration SECONDS` | Seconds to run each backend; default `5`. |
| `--output PATH` | Optional JSON report path. |
| `--model PATH` | Benchmark this specific PyTorch `.pt` model. |
| `--all-backends` | Probe every reachable backend rather than only the recommended one. |
| `--install-deps` | Best-effort install missing runtime packages for the selected backend plan. This changes the active Python environment. |

Example:

```bash
ispy-bench --model YoloModels/pytorch/my_model.pt --duration 10 --output Outputs/benchmark.json
```

### `ispy-stats`

This compares a base `.pt` model with an optimized model using images from a test directory. Pass model paths explicitly when the active camera config does not point to the pair you want to compare.

| Option | Meaning |
| --- | --- |
| `--config PATH` | Config to read model paths from; default `Config/config.json`. |
| `--base PATH` | Base `.pt` model path; overrides the config. |
| `--optimized PATH` | Converted model path; overrides the config. |
| `--images-dir PATH` | Test images; default `QuantizeDataset/valid`. |
| `--num-images N` | Number of randomly selected images; default `5`. |
| `--seed N` | Optional random seed so image selection can be repeated. |
| `--core-mask N` | RKNN NPU core mask; default `7`, ignored for other backends. |
| `--iou-thresh VALUE` | IoU threshold for matching boxes; default `0.5`. |
| `--speed-duration SECONDS` | Seconds per model in the speed test; default `5`. |
| `--output PATH` | Report path; default `Outputs/optimized_model_report.json`. |

Example:

```bash
ispy-stats --base YoloModels/pytorch/my_model.pt --optimized YoloModels/onnx/my_model.onnx --images-dir QuantizeDataset/valid --num-images 20
```

The report checks detection agreement as well as speed. Use representative images and compare with the same image set when evaluating changes; a faster artifact is not useful if it changes detections too much. Run `ispy-bench --help` or `ispy-stats --help` to confirm flags for the version installed on the robot.

Benchmark on the target machine when possible. Results from a development PC do not predict NPU performance, camera capture rate, or thermal behavior on the coprocessor. Save the JSON report with the model/version details if you need to compare runs later.

## Logs

The normal runtime appends its log to `Outputs/log.txt` under the current project directory. When started by systemd, the service output is also available through `journalctl -u iSpy -f`.

For a quick local tail:

```bash
tail -f Outputs/log.txt
```

PowerShell:

```powershell
Get-Content .\Outputs\log.txt -Tail 100 -Wait
```

Start with the first warning or error around the time the problem began. The last line is often just where the runtime noticed an earlier failure.
