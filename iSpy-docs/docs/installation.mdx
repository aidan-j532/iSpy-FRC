# Installation and Setup

There are two common installs: a Python environment on a development computer, or a provisioned Linux board that starts iSpy as a service. For a first test, use the development install below; it is easier to inspect and stop than a background service.

If you're not sure which route to choose, use the virtual-environment install first. It keeps iSpy's Python packages separate from the OS, and you can see startup messages directly in the terminal. Move to a systemd service only after the camera, model, and network path are working.

## Supported platforms

The repository includes deployment support for:

- Orange Pi 5 / 5 Pro with RK3588 NPU
- other aarch64 Linux boards, subject to camera and inference backend availability
- x86_64 Linux machines

Python package installation is also possible on Windows and macOS, but acceleration and camera support depend on the packages available for that operating system. The `install.sh` script and board provisioner are Linux shell scripts, not Windows installers. The recommended deployment target is an Orange Pi 5/5 Pro with RK3588 when you need the RKNN NPU backend. Other machines may use a different backend or CPU inference.

## Prerequisites

For a normal setup, the basics are:

- Python 3.10 or newer (the project metadata currently requires `>=3.10`)
- git
- a supported camera, USB webcam, or video source
- network access during first boot to download the default models
- the repo checked out locally, or a provisioned board image

The Python install also installs the runtime dependencies declared in `pyproject.toml`, including PyTorch, OpenCV, ONNX Runtime, and RobotPy/NetworkTables. These packages are large, and supported accelerators have additional platform requirements.

Before installing on a board, check that you have the right image for its architecture and enough storage for Python wheels and model files. A successful `pip install` only says the Python dependencies installed; it does not prove that the camera is accessible or that an accelerator runtime can use your model.

## Fresh install from the repo

Clone the repository, then create a virtual environment in the repository root. On Linux or macOS:

```bash
git clone https://github.com/aidan-j532/iSpy-FRC.git
cd iSpy-FRC
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e .
```

On Windows, use PowerShell:

```powershell
git clone https://github.com/aidan-j532/iSpy-FRC.git
cd iSpy-FRC
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e .
```

If PowerShell does not allow the activation script, run the environment's commands directly:

```powershell
.\.venv\Scripts\python.exe -m pip install -e .
.\.venv\Scripts\ispy-boot.exe -f
.\.venv\Scripts\ispy-run.exe
```

Editable mode (`-e`) means code changes in this checkout are available without reinstalling. Keep the terminal in the repository root when running iSpy; the runtime finds `Config/`, models, recordings, and logs relative to the current directory.

### Linux install script

The root `install.sh` is an alternative for Linux, not a cross-platform installer. It installs into the Python selected by `pip` and uses `--break-system-packages`; it does not create a virtual environment. It installs the base package on ARM64 and the `dev` extra on x86_64. Prefer the virtual-environment steps above unless you specifically want that system-level behavior.

### Which install path fits?

| Situation | Start with |
| --- | --- |
| Trying iSpy on a laptop or desktop | The virtual environment above |
| Developing the Python code | Editable install (`python -m pip install -e .`) |
| Deploying on a supported robot board | The board image/provisioning process, after checking its current limitations |
| Installing only to benchmark a backend | The normal package, then install an optional extra only if that benchmark needs it |

Windows PowerShell's script-execution policy may block virtual-environment activation. You do not have to change the machine-wide policy just to run iSpy: use the venv's executable directly, as shown above.

## Board image / provisioned install

The repository includes an Orange Pi image builder and a first-boot service. Keep the board connected to the network while provisioning runs. The intended service working directory is `/opt/iSpy`, where the runtime expects `Config/config.json`.

The actual provisioning script is here:

- `Image/provision.sh`
- `Image/first-boot.sh`

There is a provisioning issue in the current checkout: `Image/provision.sh` tries to copy `/opt/iSpy/Config/config.json` before running the boot command that creates it. A clean clone does not include that generated file, so first boot can stop before the service is installed. The script also creates `/etc/iSpy/config.json` and sets `iSpy_CONFIG`, but the current runtime does not read that variable. Treat the image/provision route as unverified until those paths are reconciled; see [Configuration Reference](./configuration).

## One-shot provisioner

`Image/provision.sh` is the script used by the first-boot image service. Because of the config-path issue above, do not rely on it to provision a clean Debian/Ubuntu board from this checkout. Once the script is corrected, its service can be checked with `sudo systemctl status iSpy` and `sudo journalctl -u iSpy -f`.

## Python environment notes

The normal installation includes the runtime dependencies listed in `pyproject.toml`. Optional groups are available for additional work:

- `dev` includes tools for training and conversion, including TensorFlow, ONNX packages, Jupyter, and TensorRT.
- `optimizer` includes Ultralytics and ONNX packages used by model conversion.

Install an extra only when you need it, from the repository root. For example: `python -m pip install -e ".[optimizer]"`. Some optional packages only install or run on particular operating systems and devices; an extra cannot add hardware support by itself.

Use `python -m pip` rather than a bare `pip` when possible. It makes it clear which interpreter receives the package, which avoids a common setup snag where the command is installed but the `ispy-*` entry points are not on the active environment's `PATH`.

## First boot after install

After installation, initialize a new checkout once from its root directory:

```bash
ispy-boot -f
```

This is a destructive fresh setup, not a daily startup command. It deletes `Config/`, `YoloModels/`, `Outputs/`, and the active dataset directory before recreating them. Back up your config, models, logs, and dataset files first if this is not a brand-new checkout. Boot downloads the default models, writes their metadata, creates `Config/config.json`, and may detect a connected camera. If no camera is found, you can add one later in the web UI. See [First Launch](./getting-started) for the next steps.

When setup is done, keep the project working directory in mind. Config, model, log, dataset, and recording paths are usually resolved from that directory. A service configured to run from `/opt/iSpy` and a command started from some other checkout can therefore appear to have different settings even when both use the same installed Python package.

## Before moving onto the robot

Do one complete run on the target computer with its final camera and mount:

- confirm the board sees the camera at the selected source;
- check the image at the resolution and exposure you expect to use;
- verify the chosen backend actually loads the model (not just that conversion completed);
- measure the loop rate under the model you plan to deploy;
- check disk space if recording is enabled; and
- confirm the roboRIO address from the robot network before relying on NetworkTables.

The [runtime overview](./architecture) explains which parts of that test are independent. If a clean board's image provisioner fails, consult the specific caveat above rather than repeatedly running a destructive fresh setup.
