## 1. Decouple quantization datasets from a specific .pt model

Current bug: `_dataset_dir_for()` in `iSpy/boot/boot.py` derives the
calibration dataset directory from the model's filename stem
(`QuantizeDataset/<pt_stem>/`), so calibration images are effectively owned
by one model instead of being a reusable resource.

Required end state:
- Quantization datasets live under `QuantizeDataset/<user_chosen_name>/` and
  are NOT auto-derived from any model's filename.
- Any pipeline's optimize config selects a dataset by name (this already
  partially exists — `camera_config.get("quantization_dataset")` is read in
  `object_detection.py` and `yolo_world.py` as a raw path; formalize this as
  "pick one of the named QuantizeDataset folders", not a free-text path
  people have to know in advance).
- Users can create new dataset folders and upload images into them via the
  web UI. `iSpy/web/modules/datasets.py` and `datasets.html` already support
  listing datasets, uploading images into a named dataset, and setting an
  "active" one — check whether that's sufficient or needs a "new folder"
  affordance, and whether "active dataset" should be replaced by
  "per-pipeline dataset selection" instead of one global active dataset.
- `boot.py`'s calibration/conversion call sites (`_convert_rknn`,
  `convert_model`'s tflite/openvino/engine int8 paths) must stop calling
  `_dataset_dir_for(pt_path)` as the calibration source when a named dataset
  is explicitly configured, and use the selected named dataset instead.
  Fall back to auto-generated/downloaded default calibration images only
  when no dataset is explicitly selected (preserve existing keyword-search/
  synthetic-fallback behavior in `dataset.py` for that fallback case — don't
  remove it).

Do not change the RKNN graph-surgery / quantization-collapse-fix code in
`boot.py` (`_normalize_box_coords_for_quantization`,
`_fold_scale_into_constant_input`, etc.) — that logic is unrelated and must
be left exactly as-is.

Verify: create two named datasets, point two different camera configs
(different models) at the same named dataset, run a conversion for each,
confirm both succeed using the same calibration images and neither model's
filename is required to find the dataset.

## 2. Fix `boot -f` to actually mean "wipe and start fresh", not "migrate"

Current bug: `setup_files(first_boot=True)` in `boot.py` reads the existing
`Config/config.json`, diffs it against defaults via
`_strip_boot_managed_fields`, and if it differs, **preserves and restores**
the old config after deleting YoloModels/Config/Outputs/dataset dirs. This
is the opposite of the requested behavior.

Required end state for `boot -f`:
- Delete generated state (Config, Outputs, YoloModels, quantization dataset
  dir — confirm exact list by inspecting what `setup_files` currently
  deletes) with NO attempt to read, diff, or preserve any part of the old
  config.
- After deletion, always generate a fresh default config from
  `iSpyConfig`'s `default_config` (one camera, object_detection pipeline,
  the bundled default pose model — check which of
  `_default_pose.pt`/`_default_box.pt`/`_default_v26_detect_for_fuel.pt` is
  actually the current default in `iSpyConfig.default_config` and keep using
  that one, don't invent a new default).
- Remove the `saved_config` preservation branch and the
  `_strip_boot_managed_fields` / `_default_config_dict` comparison logic
  from `setup_files` entirely (confirm these aren't used anywhere else
  before deleting — grep first).

Required end state for normal `boot` (no `-f`):
- Must NOT silently create default config if none exists. Currently
  `on_boot()` does: `if not config_path: create default`. Change this so
  missing/invalid config is a loud, clear error telling the user to run
  `boot -f`, not silent first-run behavior. Only `boot -f` may create a
  default config.

Verify: run `boot -f` twice in a row (first with no prior state, then again
with the state it just generated plus manual edits to config.json) and
confirm the second run produces byte-for-byte the same default config,
ignoring the manual edits entirely. Run plain `boot` with no config present
and confirm it errors instead of creating one.

## 3. Remove legacy top-level `vision_model` config migration

Current: `iSpyConfig._migrate_legacy_vision_model()` in
`iSpy/config/iSpyConfig.py` detects an old top-level `vision_model` key and
auto-migrates it into per-camera `vision_model` blocks, called from
`load_from_file` on every normal boot.

Required end state:
- Delete `_migrate_legacy_vision_model` and its call site entirely.
- If a config file has a top-level `vision_model` key when loaded normally,
  treat this as an invalid/outdated config and fail loudly (this is now
  covered by item 2's "normal boot doesn't silently fix broken config"
  behavior) — direct the user to `boot -f` rather than attempting to
  interpret or upgrade it.
- Check `strict_migration` parameter usage across the codebase (`iSpyConfig`
  constructor, `boot.py` call sites) and remove it if it no longer serves a
  purpose after migration is deleted — don't leave a dead parameter.

Verify: construct an `iSpyConfig` from a config file containing a top-level
`vision_model` key and confirm it errors clearly instead of migrating.

## 4. Register vision pipelines in the addons UI's `_TYPE_MAP`

Current: `iSpy/web/Backend/PluginStatus.py`'s `_TYPE_MAP` only covers
tracker/utility/frame_processor. Vision pipelines
(`iSpy/vision/pipelines/`) are loaded via a separate static `PIPELINES`
dict in `vision/pipelines/__init__.py` and can't be toggled/uploaded/deleted
through `/addons` the way other plugin types can.

Required end state:
- Add a `vision_pipeline` (or matching name) entry to `_TYPE_MAP` pointing
  at the pipelines directory and `VisionBase`.
- Check whether `_TYPE_MAP`'s assumption (loader scans a directory of
  standalone .py files via `load_plugins`) is compatible with how
  `vision/pipelines/__init__.py` registers pipelines (explicit static
  `PIPELINES` dict, not directory scanning) — these are two different
  loading strategies and need to be reconciled, not silently duplicated.
  Determine whether built-in pipelines (april_tag, object_detection, etc.)
  should be excluded from toggle/delete (since they're core, not
  user-added) the same way `BuiltIn/` trackers/utilities already are
  excluded in `_delete()`'s `"BuiltIn" in path.parts` check.
- User-authored pipelines dropped into a new pipelines-plugin directory
  (if one doesn't exist yet, check whether this task requires creating
  `plugins/vision/` per the older architecture notes, or whether pipelines
  are meant to stay code-only/non-pluggable — confirm before adding new
  directory scanning).

Verify: built-in pipelines show up in `/addons` as non-deletable; if a
plugin-style vision pipeline directory is added, a dropped-in custom
pipeline .py file appears in the available list and can be
enabled/disabled without editing `vision/pipelines/__init__.py`.
