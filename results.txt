# iSpy Add-ons Restructure - Extensive Summary

## What I did (TL;DR)

Reworked add-on (plugin) configuration from a list of active add-on names into a
dictionary of enabled add-on -> its OWN settings, mirroring how vision
pipelines were restructured earlier (per-camera `pipeline: {name, settings}`):

```jsonc
"plugins": {
    "trackers": {
        "object_tracker": { "distance_threshold": 0.5, "stale_threshold": 1.0 },
        "path_planner":   { "epsilon": 0.3, "min_samples": 3 }
    },
    "utilities": {
        "network_table_handler": { "network_tables_ip": "10.0.0.2" },
        "video_recorder":       { "record_dir": "VideoRecordings" }
    },
    "frame_processors": {
        // none enabled - empty dict
    }
}
```

Presence == ENABLED. There is no "enabled" flag anywhere. Removing an add-on's
dict entry disables it; adding an entry enables it. Every add-on's settings now
live inside its own entry, and settings that used to be global config keys move
into the add-on they belong to:

| Old global key           | Now lives in                              |
|--------------------------|-------------------------------------------|
| `dbscan.epsilon`         | `plugins.trackers.path_planner.epsilon`   |
| `dbscan.min_samples`     | `plugins.trackers.path_planner.min_samples` |
| `distance_threshold`     | `plugins.trackers.object_tracker.distance_threshold` |
| `stale_threshold`        | `plugins.trackers.object_tracker.stale_threshold` AND `plugins.utilities.health_reporter.stale_threshold` |
| `use_network_tables`     | REMOVED - presence of `network_table_handler` == enabled |
| `network_tables_ip`      | `plugins.utilities.network_table_handler.network_tables_ip` |
| `record_mode`            | REMOVED - presence of `video_recorder` == enabled |
| `record_dir`             | `plugins.utilities.video_recorder.record_dir` |

Vision pipelines were NOT restructured. They remain core code selected per
camera via the `pipeline` key (their only contact with this change is that
consumers which previously read global keys now read per-add-on settings).

## Why

- **One source of truth per add-on**: an add-on is fully described by its
  config entry - enabled state + all of its settings in one place.
- **No dangling "enabled but unconfigured" states** (e.g. `use_network_tables:
  true` with a missing/empty IP was possible before; now the entry ships its own
  IP).
- **Settings belong to the feature they configure**, not to the global config,
  so enabling an add-on can't accidentally leak into unrelated add-ons.
- **Matches the pipeline pattern** the codebase already adopted, so the config
  has one mental model - dict of name -> settings everywhere.
- **Forward-only & typo-proof config**: the settings save API validates every
  key against the add-on's declared schema before it can reach the config.

## How it works

### Config layout & migration (`iSpy/config/iSpyConfig.py`)

- New `_migrate_addons()` runs at load (after `_check_config`, before
  `_migrate_camera_configs`) and is **idempotent**: old configs load fine and
  self-upgrade. Rules:
  - `plugins.<type>` lists (`["object_tracker"]`) become dicts
    (`{"object_tracker": {}}`); non-dict junk is sanitized.
  - Legacy top-level settings are folded into the add-on they belong to, but
    ONLY into add-ons that are already enabled - migration never enables an
    add-on that was disabled.
  - `use_network_tables: true` / `record_mode: true` become presence of
    `network_table_handler` / `video_recorder`; the flag values are discarded.
  - All legacy global keys are removed from the config afterwards.
- Default config no longer contains `dbscan`, `distance_threshold`,
  `stale_threshold`, `record_mode`, `record_dir`, `use_network_tables`,
  `network_tables_ip` - they moved into (or out of) the add-on dicts.
- New helpers on `iSpyConfig`:
  - `addon_entries(type)` - enabled add-ons of a type (dict)
  - `get_addon_settings(type, name)` / `get_addon_setting(type, name, key, default)`
  - `is_addon_enabled(type, name)`
  - `enable_addon(type, name, settings=None)` / `disable_addon(type, name)`
  - `set_addon_settings(...)` / `update_addon_settings(...)`
  - each persists with `save()` unless `save=False`.

### Add-on runtime view (`iSpy/plugins/bases.py`)

- New `AddonBase` sits under `TrackerBase` / `UtilityBase` /
  `FrameProcessorBase`. Every add-on is constructed with a **context dict**:
  - `context["config"]` - `iSpyAddonConfig` view of THIS add-on's own settings
    (schema defaults merged in, nothing persisted).
  - `context["global_config"]`, `context["cameras"]`, `context["flask_app"]`,
    `context["vision_instance"]` for shared access.
- `config_schema()` classmethod mirrors the vision pipeline pattern:
  ```python
  @classmethod
  def config_schema(cls):
      return {
          "distance_threshold": {"type": "number", "label": "Merge Distance (m)",
                                 "default": 0.5, "hint": "..."},
      }
  ```
  Types: `number`, `text`, `toggle`. `AddonBase.default_settings()` resolves
  `{key: default}` from the schema; the loader merges these defaults in at
  construction, so an entry of `{}` just works and omitted keys keep their
  defaults without being written back to the config.
- `iSpyAddonConfig` (in `iSpyConfig.py`) is a thin settings view with
  `get/get_nested/set/setdefault/items/keys/to_dict/__getitem__/__contains__`,
  mirroring `iSpyCameraConfig`.

### Add-on loading (`iSpy/iSpy.py`)

- `_enabled_addons(type)` yields `(name, settings)` pairs from the dict.
- `_addon_context(cls, settings)` builds each instance's context with its own
  settings view.
- Trackers now receive the same context dict as utilities/frame processors
  (previously they got the raw global config - inconsistent).
- Unknown add-on names in config are logged and skipped (no crash).

### Each built-in add-on

- **object_tracker**: reads `distance_threshold` (0.5) and `stale_threshold`
  (1.0) from its own settings; negative/invalid threshold still falls back to
  0.5 with a warning.
- **path_planner**: reads flattened `epsilon` (0.3) and `min_samples` (3) from
  its own settings (old global `dbscan` dict migrated + flattened).
- **network_table_handler**: no more `_enabled`/`use_network_tables` check -
  presence IS the switch; reads `network_tables_ip` (10.0.0.2) from its own
  settings. `isConnected()` is now purely "instance is connected".
- **video_recorder**: no more `record_mode` check - presence IS the switch;
  reads `record_dir` (VideoRecordings) plus newly-exposed `fps` (30.0),
  `max_queue` (300), `downsample` (1) from its own settings (all default to the
  previously hard-coded values, so behavior is unchanged unless you set them).
- **health_reporter**: reads `stale_threshold` (1.0) from its own settings.
- **Examples** (`example_tracker`, `example_utility`,
  `example_frame_processor`) rewritten to demonstrate the new context/settings
  pattern with `config_schema()`.

### Web layer

- `/api/plugins/available` now returns, per add-on: `enabled` (presence), the
  full `config_schema`, and the add-on's current `settings`.
- `/api/plugins/toggle` enables/disables by adding/removing the dict entry
  (`enable_addon` / `disable_addon`).
- NEW `/api/plugins/settings` (POST: `{name, type, settings}`) validates and
  coerces every key against the add-on's schema (unknown keys and bad numbers
  are rejected with a 400), merges into the enabled add-on's entry, saves, and
  requires a vision restart. Saving settings for a disabled add-on returns 409
  (presence == enabled, so a disabled add-on has no settings slot).
- `addons.html` gained an inline settings editor modal rendered from the
  schema (number/text/toggle fields, with labels and hints), so the IP,
  thresholds, record dir, etc. are editable in the UI. Built-in vision
  pipelines remain read-only listings.
- Deletion disables the add-on in config first (via the same dict semantics).

### Consumers updated to the new world (not resting on old global keys)

- `web/modules/health.py` + `web/Backend/Status.py`: stale threshold read from
  `plugins.utilities.health_reporter` (schema default 1.0).
- `web/Backend/SetupWizard.py`: the legacy wizard payload
  (`use_network_tables` / `network_tables_ip`) is translated into enabling the
  `network_table_handler` add-on with its own IP; no global keys are written.
- `web/Backend/Settings.py`: `_RESTART_REQUIRED_KEYS` trimmed of the moved
  keys (the whole `plugins` dict already restarts vision).
- `validations/recommendations.py`: DBSCAN/NT/dist-threshold checks read from
  the corresponding add-on entries, and are skipped when the add-on is not
  enabled.
- `validations/validate_system.py`: NT IP validation + recommendations read
  add-on settings; added local `get_addon_setting` helper for raw dicts.
- `Config/config.json` migrated to the new structure in the repo.
- `iSpy/web/templates/settings.html`: removed the legacy global-key form rows
  (they would have resurrected the removed keys on save); replaced with
  pointers to the Add-ons page. `BOOL_KEYS` trimmed.

## Gaps I filled that you didn't spell out

1. Per-add-on declarative **settings schemas** (`config_schema()`) so the web
   UI can render an editor and defaults resolve at runtime.
2. **Settings editing UI** on the Add-ons page (without it the NT IP you
   called out would have no UI to configure it).
3. **Auto-migration** of existing configs - your saved Config/config.json
   upgrades in place, nothing is lost for enabled add-ons.
4. **Validation & coercion** on settings saves so the config stays
   forward-only and typo-proof.
5. Reading `stale_threshold` for the health page/status from the
   health_reporter add-on instead of a removed global key.
6. Setup wizard translates its legacy NT form fields into add-on presence.
7. Config helpers (`enable_addon`, `disable_addon`, `get_addon_setting`, ...)
   so no part of the codebase pokes `config["plugins"]` by hand.
8. Removed the stale legacy fields from the Settings page so saving it can't
   resurrect removed global keys.

## Notes / edge cases

- Migration folds legacy global settings only into add-ons that were already
  enabled. If you had a global `stale_threshold` but no health_reporter/object
  tracker enabled, the value is dropped (defaults apply when you enable them
  later).
- Add-ons whose schema has no settings (e.g. the examples) still work as
  before: the presence entry is just `{}`.
- The `status_reporter`/`DatasetManager`/`YOLOHandler` classes that subclass
  UtilityBase outside the plugin dirs are not loaded by the plugin loader and
  were only kept interface-compatible (Status.py reads the new helper).
- Built-in pipelines remain listed read-only in /addons; they are selected per
  camera and cannot be toggled/deleted here (unchanged).
