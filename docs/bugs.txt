BUG 4 — torch.load(weights_only=False) reachable from public upload endpoint (P0, security)
============================================================

File: iSpy/vision/genericYolo.py (torch_load), iSpy/web/modules/models.py
(ModelsModule._upload)

Context: torch_load() in genericYolo.py hardcodes weights_only=False when
calling torch.load, because the dependency-free yolo_pt shim needs to
reconstruct custom nn.Module classes (Conv, C2f, DFL, etc.) that
weights_only=True's restricted unpickler would reject. That's a legitimate
need for TRUSTED local model files. The problem: ModelsModule._upload()
(iSpy/web/modules/models.py) accepts an unauthenticated .pt upload via
POST /api/models/upload, saves it to a temp path, and immediately calls
metadata_from_pt(tmp) -> torch_load(tmp) on the raw uploaded bytes BEFORE
any validation. This is arbitrary pickle deserialization from an
unauthenticated network endpoint - a full RCE surface.

Steps:
1. Confirm the call chain: _upload() -> metadata_from_pt() (iSpy/vision/
   metadata.py) -> torch_load() (iSpy/vision/genericYolo.py) -> the
   register_shim() + torch.load(weights_only=False) call. Confirm no
   validation happens on the uploaded bytes before this call.
2. Do NOT globally flip weights_only=True - that breaks the legitimate
   yolo_pt shim reconstruction path for already-trusted local models
   (YoloModels/pytorch/*.pt placed by boot.py, the optimizer, or picked
   from the local library). The fix is restricting what's deserializable
   FROM THE UPLOAD PATH specifically, not changing trust behavior for
   models already on disk.
3. Fix options (pick the one that fits without breaking the shim, verify
   by testing an actual pose .pt upload still works after the fix):
   a. Add a pre-load structural check on the upload path: use
      torch.load(tmp, map_location="cpu", weights_only=True) FIRST as a
      cheap sanity pass; if that fails (expected, since it's a real
      Ultralytics checkpoint with custom classes), fall back to the
      shimmed weights_only=False load, but ONLY after confirming the
      pickle's declared classes are limited to the known-safe shim
      registry (use torch.serialization.add_safe_globals to explicitly
      allowlist iSpy.vision.yolo_pt's classes for weights_only=True instead
      of disabling it - check whether the installed torch version supports
      add_safe_globals; this is the correct long-term fix if available).
   b. If add_safe_globals isn't viable on the supported torch version,
      require the upload endpoint to run the untrusted load in a
      subprocess with no filesystem/network access beyond writing the
      validated result, mirroring the _convert_worker.py subprocess
      isolation pattern already used elsewhere in this codebase. The
      subprocess boundary limits blast radius even if the pickle exploits
      something.
4. Require ISPY_ADMIN_TOKEN or local-only access on POST /api/models/upload
   the same way iSpy/web/Backend/PluginStatus.py's require_local_or_token
   decorator already gates /api/plugins/upload - confirm whether
   ModelsModule._upload currently has ANY auth gate (it does not appear
   to). Add the same decorator.
   4a. While here, grep for every route in iSpy/web/modules/ and
       iSpy/web/Backend/ that accepts request.files or writes to disk from
       a POST body, and confirm each one either has require_local_or_token
       or a documented reason it doesn't need it (e.g. dataset image
       upload in datasets.py, addon upload in PluginStatus.py - the latter
       should already be gated, confirm rather than assume). Report any
       gap found even if out of scope to fix here.
5. Add a test that a malicious/malformed .pt (e.g. a pickle containing a
   disallowed class not in the shim registry) is rejected before reaching
   torch.load, not silently swallowed into a 500.
6. Report: which fix (3a or 3b) was applied and why, confirm existing
   legitimate model uploads (detect + pose) still work post-fix, confirm
   the auth gate is in place, report findings from 4a.

BUG 6 — ObjectDetectionPipeline model-config ValueError not caught locally (P2)
============================================================

File: iSpy/vision/pipelines/object_detection.py

Context: ObjectDetectionPipeline.__init__ calls
fill_missing_config(dict(vm_cfg)) (iSpy/vision/ModelInspector.py) BEFORE
the try/except (ModelFileError, ValueError) block that wraps
GenericYolo(vm_filled, ...). If fill_missing_config() itself raises
ValueError (it can, e.g. via inspect_model()'s format-detection path), that
exception is NOT caught locally in ObjectDetectionPipeline.__init__ - it
propagates up to iSpy.py:_build_cameras_from_config's `except Exception`
wrapper, which logs and skips the camera entirely. This means: instead of
the camera appearing with an "error: <reason>" status (like a bad
GenericYolo load produces via the existing try/except), the camera simply
never appears in self.cameras at all - no dashboard entry, no is_ready()
status, nothing. This is a silent-ish failure mode, not a crash, but it's
inconsistent with the ModelFileError/ValueError-from-GenericYolo path 30
lines later in the same function, which DOES surface a clean per-camera
error status.

Steps:
1. Confirm by tracing: does fill_missing_config() have any code path that
   raises ValueError given a legitimately-bad-but-plausible vm_cfg (e.g.
   malformed input_size, a model file that exists but fails
   inspect_model())? Check inspect_model()'s dispatch and each _inspect_*
   helper for raise ValueError(...) calls reachable from a normal (not
   adversarial) misconfiguration.
2. Wrap the fill_missing_config(dict(vm_cfg)) call (and the subsequent
   vm_filled = ... line) in the SAME try/except (ModelFileError, ValueError)
   pattern already used around GenericYolo(...) a few lines later, logging
   the same style of error and leaving self.model = None instead of
   propagating. Camera construction should still succeed (so the camera
   appears with an error status) rather than being skipped entirely.
3. Do NOT change behavior for any OTHER exception type raised here (e.g. a
   genuine bug) - only ModelFileError/ValueError, consistent with the
   existing pattern's intent (these two are "bad model config", not "iSpy
   bug").
4. Add a test: construct ObjectDetectionPipeline with a vm_cfg that causes
   fill_missing_config to raise ValueError, assert the pipeline still
   constructs successfully with self.model is None and is_ready() reports
   "error: ..." rather than the constructor raising. Also assert a
   logger.error (or equivalent) call actually fired with the underlying
   reason - the failure must be loud in Outputs/log.txt, not just
   swallowed into a quiet None.
5. Report: confirm this doesn't change behavior for the already-passing
   "model file missing" and "model file corrupt" test cases in
   TestGenericYoloModelSelection (iSpy/validations/unit_tests.py) - those
   exercise GenericYolo directly, not ObjectDetectionPipeline.__init__, so
   should be unaffected, but verify.
